================================================================================
EKLK — BACKEND SCALE PLAN
================================================================================
Дата: 2026-08-28
Целевая ветка: exp (реализацию выполнять поэтапно через expbd → dev → main)
Цель: подготовить backend EKLK к стабильной работе с сотнями одновременных
пользователей и горизонтальному запуску в 2–4+ worker/process без изменения
бизнес-контрактов текущего ЛК.

СТАТУС: ПЛАН РЕАЛИЗАЦИИ

ВАЖНО: этот документ является рабочим планом. Не пытаться реализовать всю
задачу одним большим изменением в production. Допускается ОДИН большой
промпт для AI-агента только как оркестратор этапов: агент обязан сначала
проанализировать код, затем выполнить этапы последовательно, запускать тесты
после каждого этапа и останавливать работу при регрессии. Предпочтительный
вариант — 5–7 отдельных промптов/PR, потому что этапы C/D затрагивают
авторизацию и сессионную модель и требуют независимого отката.

================================================================================
1. РЕЗУЛЬТАТ, КОТОРЫЙ ДОЛЖЕН ПОЛУЧИТЬСЯ
================================================================================

После завершения плана:

- приложение работает без --reload в production;
- 2–4 worker/process используют единое состояние пользовательских сессий;
- restart одного worker не выбивает пользователя из ЛК;
- login → F5 → select-store → create check → orders работают между worker'ами;
- HTTP-соединения к EcomKassa переиспользуются, а не создаются на каждый
  запрос;
- пароль пользователя не хранится открытым текстом в Redis/session store;
- настройки имеют устойчивое хранилище и не зависят от памяти worker'а;
- есть rate limit для login и тяжёлых операций;
- есть ограничение исходящей конкуренции к EcomKassa;
- health/logging/metrics позволяют понять, где находится узкое место;
- существующие URL, JSON-контракты фронта, Bearer JWT и бизнес-логика чеков
  не меняются без доказанной необходимости.

Не является целью:
- переписать app.js;
- перейти на новый frontend framework;
- менять Atol Online v5 / ФФД / СНО / payments.type;
- менять бизнес-логику чеков, возвратов, ссылок, каталога, отчётов;
- превращать EKLK в самостоятельную систему хранения всех заказов.

================================================================================
2. ЧТО УЖЕ ЕСТЬ И ГДЕ РИСК
================================================================================

По текущему коду ветки exp:

- FastAPI backend;
- app/core/deps.py содержит SESSIONS = dict в RAM;
- session хранит login, password, group_code, firm, selected_store_id;
- JWT проверяется, но после рестарта/на другом worker session может отсутствовать;
- app/clients/ecomkassa.py создаёт собственный httpx.AsyncClient в каждом
  экземпляре EcomKassaClient;
- token EcomKassa сейчас кэшируется только внутри экземпляра клиента;
- settings используют отдельное хранилище, которое должно оставаться
  совместимым с текущим degraded-поведением;
- frontend app.js — стабильное монолитное ядро и не должен участвовать в
  масштабировании, кроме точечного критического изменения.

Главные проблемы масштабирования:

1) RAM sessions → multi-worker/restart ломают авторизацию.
2) plaintext password в session → повышенный ущерб при дампе памяти/Redis.
3) AsyncClient на экземпляр → лишние TCP/TLS соединения и риск роста FD.
4) отсутствие централизованного лимита исходящих запросов → можно перегрузить
   app.ecomkassa.ru быстрее, чем пользовательский UI успеет это заметить.
5) SQLite при активной записи → потенциальные database is locked.
6) отсутствие нормальной наблюдаемости → трудно отличить проблему EKLK от
   проблемы upstream EcomKassa.

5. ЭТАП B — SHARED HTTPX CLIENT
================================================================================

Файлы:
- eklk/app/main.py
- eklk/app/clients/ecomkassa.py
- при необходимости routers, только точечно.

Сделать:

B1. Создать один httpx.AsyncClient на process через FastAPI lifespan.

B2. Настроить httpx.Limits с разумными пределами max_connections и
    max_keepalive_connections.

B3. Настроить единый timeout, ориентировочно 30 секунд, без бесконечных
    запросов.

B4. Передавать shared client в EcomKassaClient вместо создания нового
    AsyncClient внутри каждого экземпляра.

B5. На shutdown выполнять await client.aclose().

B6. Не менять публичную семантику get_token/create_sell/create_refund/
    get_report/search_orders/get_order/catalog/reports.

B7. Если требуется сохранить совместимость с существующим кодом, допускается
    временный optional client=...; старый путь не должен оставаться скрытым
    источником утечки ресурсов в production.

Проверка:
- login + firm;
- create check;
- payment/invoice;
- orders;
- catalog;
- reports;
- длительный прогон 300–1000 запросов.

Acceptance:
- AsyncClient не создаётся на каждый request/client instance;
- соединения переиспользуются;
- FD/socket count не растёт линейно с числом запросов.

================================================================================
6. ЭТАП C — REDIS SESSION STORE
================================================================================

Это КЛЮЧЕВОЙ этап для multi-worker.

Файлы:
- eklk/app/core/deps.py
- новый service/module session store;
- eklk/app/core/config.py
- requirements.txt
- .env.example
- тесты.

Архитектура:

SessionStore interface:
    save_session(...)
    get_session(login)
    update_session_store(login, store_id)
    clear_session(login)

Реализации:
    MemorySessionStore — dev/fallback
    RedisSessionStore — production

Конфигурация:
    SESSION_BACKEND=memory|redis
    REDIS_URL=redis://...

Redis key:
    eklk:session:{login}

TTL:
    не меньше срока жизни JWT, с небольшим запасом.

ВАЖНО:
На этапе C допускается временно сохранить password для совместимости.
Его удаление — отдельный этап D. Не смешивать две рискованные миграции.

Failure policy:
- dev/fallback: memory + warning;
- production рекомендуется fail-fast/503 при невозможности создать
  авторизованную session, если иначе пользователь может получить непредсказуем
  state split между worker'ами.

Проверка:
1. Запустить два worker.
2. Login.
3. Несколько раз F5.
4. Сделать запросы так, чтобы они попадали в разные worker.
5. select-store на worker A.
6. create check / orders на worker B.
7. logout.

Acceptance:
- session едина для всех worker;
- restart одного worker не выбивает session;
- selected_store_id синхронизирован;
- JWT остаётся Bearer JWT в том же формате.

================================================================================
7. ЭТАП D — УБРАТЬ PLAINTEXT PASSWORD ИЗ SESSION
================================================================================

Это самый чувствительный этап. Делать только после C.

Цель session:
    login
    ecom_token
    ecom_token_expires_at (если возможно определить)
    group_code
    selected_store_id
    firm

Password не должен храниться в Redis открытым текстом.

Алгоритм:

D1. Login:
    credentials → getToken → сохранить ecom_token → password выбросить.

D2. Обычные Ecom-запросы используют сохранённый ecom_token.

D3. Если EcomKassa отвечает 401:
    - выполнить ОДИН refresh/re-auth, если есть безопасный способ;
    - иначе вернуть контролируемый 401 «войдите снова».

D4. Не допускать бесконечного refresh loop.

D5. Не писать token/password в logs.

D6. Проверить race condition при одновременном refresh одного пользователя:
    нужен lock/atomic strategy, чтобы 20 параллельных запросов не делали
    20 getToken.

Если для refresh обязательно нужен password, выбрать один из вариантов:
1) короткоживущий encrypted secret, зашифрованный ключом приложения;
2) другой поддерживаемый механизм EcomKassa;
3) принудительный повторный login.

Не изобретать собственный криптографический протокол.

Acceptance:
- Redis dump не содержит password в открытом виде;
- token используется повторно;
- 401 корректно обрабатывается;
- параллельный refresh не создаёт storm запросов.

8. ЭТАП E — SETTINGS DB / POSTGRESQL
================================================================================

Не менять API настроек.

Цель: исключить SQLite locking на production при заметной записи.

Вариант production:
    DATABASE_URL=postgresql+asyncpg://...

SQLite:
    оставить для dev/test.

Сохранить существующие сущности:
- user_settings
- firm_settings
- JSON preferences, если они используются сейчас.

Сохранить degraded-поведение:
- проблема БД не должна превращать весь ЛК в 500;
- GET/PUT /api/v1/auth/settings остаются совместимыми.

Проверка:
- theme light/dark/glass;
- настройки организации;
- выбранный магазин;
- параллельные PUT;
- отключение БД → ожидаемый degraded response.

Решение «делать сразу или позже»:
- до ~50–100 активных пользователей SQLite может оставаться допустимым,
  если запись редкая;
- для production 200+ и нескольких worker предпочтителен PostgreSQL.

================================================================================
9. ЭТАП F — RATE LIMIT + UPSTREAM PROTECTION
================================================================================

F1. Login:
    жёсткий rate limit по IP.

F2. Create check/payment:
    мягкий rate limit по authenticated user/session.

F3. Исходящие запросы к EcomKassa:
    asyncio.Semaphore на process.
    Начальное значение подобрать тестом, например 50–100, не считать это
    магической константой.

F4. Таймауты едины и конечны.

F5. Не ставить настолько агрессивные лимиты, чтобы обычная навигация,
    F5 и работа нескольких вкладок блокировались.

Acceptance:
- burst login получает 429;
- один проблемный пользователь не забивает весь upstream pool;
- остальные пользователи продолжают работать.

- какой endpoint;
- сколько занял EKLK;

Метрики минимум:

- upstream latency;
- upstream errors;
- Redis errors;
- DB errors;

- 429 count.

Health:
    GET /health

Расширить без поломки существующего ответа:
    app=ok
    redis=ok|skip|degraded
    db=ok|degraded

Не отдавать секреты и внутренние connection strings.

- API latency остаётся предсказуемой при росте concurrency.

14. МОЖНО ЛИ СДЕЛАТЬ ОДНИМ ПРОМПТОМ?
================================================================================

Технически — ДА, но только как master prompt для автономного агента.
Практически для production — НЕ РЕКОМЕНДУЕТСЯ делать одной непрерывной
генерацией без остановок.

Причины:
- C меняет модель хранения session;
- D меняет credential lifecycle;
- E меняет БД;
- F меняет поведение при высокой нагрузке;
- ошибки C/D трудно локализовать, если всё смешать;
- большой diff сложнее ревьюить и откатывать.

Оптимальный режим:

PROMPT 1: A+B — конфиг + shared HTTP client
PROMPT 2: C — Redis session store
PROMPT 3: D — token lifecycle / убрать password
PROMPT 4: E — PostgreSQL settings
PROMPT 5: F — rate limits + upstream semaphore
PROMPT 6: G+H — observability + load/regression tests

Если AI хорошо умеет выполнять долгие задачи, можно дать master prompt,
но в нём прямо потребовать остановку после каждого этапа и подтверждение
тестов перед переходом дальше.
