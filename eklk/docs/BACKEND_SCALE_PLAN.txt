================================================================================
EKLK — план доработки backend под нагрузку (200–1000 пользователей)
================================================================================
Дата: 2026-08-27
Ветки: exp / expbd / dev
Принцип: НЕ ломать текущую бизнес-логику (чеки, ссылки, возвраты, ФФД, СНО,
магазины, каталог, отчёты, ИИ-кассир). Только инфраструктура сессий, I/O, конфиг.

Статус документа: план. Реализация — поэтапно, с проверкой login / F5 / create
check / orders / select-store после каждого этапа.


--------------------------------------------------------------------------------
0. ЦЕЛЬ И ОГРАНИЧЕНИЯ
--------------------------------------------------------------------------------

Цель:
  - стабильная работа при одновременной работе сотен операторов;
  - возможность 2+ worker’ов uvicorn/gunicorn без «Сессия истекла»;
  - меньше риска утечек сокетов и database is locked;
  - без изменения контрактов API для фронта (URL, JSON, JWT в Authorization).

Не делаем в этом плане:
  - рефакторинг app.js / переписывание форм чека;
  - смена протокола EcomKassa / полей ФФД;
  - обязательный отказ от прокси-модели (ЛК остаётся тонким слоем).

Правило совместимости:
  - фронт продолжает слать Bearer JWT как сейчас;
  - /api/v1/* пути и тела запросов не менять без крайней нужды;
  - при недоступности Redis/БД — предсказуемый fallback (как сейчас degraded
    для settings), а не 500 на весь ЛК.


--------------------------------------------------------------------------------
1. ТЕКУЩЕЕ СОСТОЯНИЕ (кратко)
--------------------------------------------------------------------------------

  - SESSIONS: dict в RAM (login → password, group_code, firm, selected_store_id)
  - JWT HS256, subject = login; без записи в SESSIONS API отвечает 401
  - На каждый запрос к Ecom: новый EcomKassaClient + httpx.AsyncClient
  - Settings: SQLite (user_settings / firm_settings), при сбое — degraded
  - Запуск: один uvicorn, часто с --reload

Риски: multi-worker, рестарт, plaintext password в RAM, сокеты, SQLite lock,
упор в upstream app.ecomkassa.ru.


--------------------------------------------------------------------------------
2. ЭТАПЫ (порядок важен)
--------------------------------------------------------------------------------

Этап A — прод-конфиг (1–2 часа, без смены логики)
Этап B — общий httpx-клиент (lifespan)
Этап C — сессии во внешнем store (Redis), совместимый API get_session/save_session
Этап D — не хранить пароль в сессии (ecom token + refresh)
Этап E — БД settings → PostgreSQL (или оставить SQLite при малой записи)
Этап F — лимиты и защита (rate limit, upstream concurrency)
Этап G — наблюдаемость (логи/метрики без секретов)

Каждый этап = отдельный PR/коммит в expbd → проверка → dev.


================================================================================
ЭТАП A. Продакшен-конфиг
================================================================================

Файлы: .env / .env.example, app/core/config.py, start-eklk.sh, README

A1. Обязательные переменные на проде:
    SECRET_KEY          — длинная случайная строка (≥32), НЕ дефолт из репо
    DEBUG=false
    LOG_LEVEL=INFO
    ACCESS_TOKEN_EXPIRE_MINUTES — по политике (сейчас 480)

A2. Запуск без --reload:
    uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
    (workers > 1 только после этапа C)

A3. Проверка:
    - login / logout / F5
    - создание чека, список чеков
    - в логах нет паролей

Критерий готовности: один worker, стабильный secret, debug выключен.


================================================================================
ЭТАП B. Общий HTTP-клиент к EcomKassa
================================================================================

Цель: не открывать AsyncClient на каждый API-запрос; не менять сигнатуры
роутеров.

B1. В app/main.py lifespan:
      - создать httpx.AsyncClient(timeout=..., limits=httpx.Limits(...))
      - сохранить в app.state.http / module-level get_http_client()
      - на shutdown: await client.aclose()

B2. EcomKassaClient:
      - принимать optional client= или брать shared client
      - НЕ создавать новый AsyncClient в __init__, если передан shared
      - методы get_token / create_check / search_orders — без изменения
        внешней семантики

B3. _client_for(user) в routers:
      - по-прежнему передаёт login, password, group_code
      - внутри использует shared httpx

B4. Проверка:
      - login, firm profile, create check, orders search, catalog, reports
      - длительный прогон (сотни запросов) — рост FD не линейный

Откат: вернуть создание AsyncClient в EcomKassaClient — логика чеков та же.

Критерий: один пул соединений на процесс.


================================================================================
ЭТАП C. Сессии вне RAM (Redis) — ключ к multi-worker
================================================================================

Цель: SESSIONS доступны всем worker’ам; интерфейс deps.py сохранить.

C1. Абстракция (минимальная):
      save_session(login, password, group_code=..., firm=...)
      get_session(login) -> dict | None
      update_session_store(login, store_id)
      clear_session(login)

    Реализации:
      - MemorySessionStore  (текущее поведение, default)
      - RedisSessionStore   (SESSION_BACKEND=redis)

C2. Redis:
    ключ: eklk:session:{login}
    TTL: согласовать с ACCESS_TOKEN_EXPIRE_MINUTES (например + небольшой запас)
    value: JSON {login, password?, group_code, firm, selected_store_id, ...}

C3. Конфиг:
    SESSION_BACKEND=memory|redis
    REDIS_URL=redis://...

C4. Поведение при недоступности Redis:
    вариант 1 (предпочтительный на старте): fallback в memory + warning в лог
    вариант 2 (строгий прод): 503 на login с понятным сообщением

C5. Проверка:
    - 2 worker’а uvicorn: login на одном, API на другом — без «Сессия истекла»
    - select-store виден с обоих worker’ов
    - logout / clear_session
    - F5, повторный вход

Важно: формат JWT и заголовок Authorization не менять.

Критерий: workers≥2 работают с одной «логикой сессии».


================================================================================
ЭТАП D. Убрать plaintext password из сессии (после C)
================================================================================

Сейчас password нужен, чтобы на каждый запрос получать token EcomKassa.

D1. В сессии хранить:
      - ecom_token
      - ecom_token_expires_at (если API отдаёт / эвристика)
      - login, group_code, firm, selected_store_id
    Password — только в момент login, не писать в Redis (или шифровать
    ключом SECRET_KEY, если без password refresh невозможен).

D2. EcomKassaClient:
      - режим «уже есть token» без login/pass на каждый вызов
      - при 401 от Ecom — один refresh:
          если есть secure password blob → getToken снова
          иначе → 401 клиенту ЛК «войдите снова»

D3. Не менять:
      - тела create check / payment / orders для фронта
      - выбор group_code = storeId

D4. Проверка:
    - полный сценарий чека и ссылки
    - истечение ecom token (симуляция) → refresh или корректный re-login
    - в Redis/логах нет пароля открытым текстом

Критерий: компрометация дампа Redis не раскрывает пароли пользователей.


================================================================================
ЭТАП E. Settings DB
================================================================================

E1. При росте записи настроек:
    DATABASE_URL=postgresql+asyncpg://...

E2. Миграции: сохранить схему user_settings / firm_settings (JSON prefs).
    SQLite оставить для dev (.env.example).

E3. Не менять контракт:
    GET/PUT /api/v1/auth/settings
    degraded: true при сбое — как сейчас

E4. Проверка: тема, select-store persistence, degraded при выключенной БД.

Критерий: нет массовых "database is locked" на проде.


================================================================================
ЭТАП F. Лимиты и защита
================================================================================

F1. Rate limit (например slowapi / middleware):
    - POST /api/v1/auth/login  — жёсткий лимит с IP
    - тяжёлые POST (create check, payment) — мягкий лимит с user id

F2. Ограничить параллельные исходящие запросы к EcomKassa
    (asyncio.Semaphore на процесс, например 50–100).

F3. Таймауты: оставить разумные (30s), не бесконечные; единый read timeout.

F4. Проверка: при бурсте login — 429, остальные пользователи работают.

Не блокировать легитимный UI (F5, навигация по вкладкам).

================================================================================
4. РЕКОМЕНДУЕМЫЙ ПОРЯДОК ВНЕДРЕНИЯ НА ПРОД
================================================================================

  1) Этап A на текущем одном сервере
  2) Этап B (httpx) — снижение риска по сокетам
  3) Поднять Redis → Этап C → включить --workers 2..4
  4) Этап D (без пароля в store)
  5) Этап E при росте settings или сразу на Postgres
  6) Этап F/G по мере появления трафика

Ориентир по пользователям:
  - до ~50–100 активных операторов, 1 worker: A+B достаточно
  - 200+ online / несколько worker’ов: C обязателен
  - 1000 concurrent active: C+D+E+F, контроль лимитов upstream
