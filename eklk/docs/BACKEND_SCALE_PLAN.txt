1. РЕЗУЛЬТАТ, КОТОРЫЙ ДОЛЖЕН ПОЛУЧИТЬСЯ
================================================================================

После завершения плана:

- приложение работает без --reload в production;
- production запускается ровно с 2 worker/process;
- оба worker используют единое состояние пользовательских сессий;
- restart одного worker не выбивает пользователя из ЛК при живом втором worker;
- login → F5 → select-store → create check → orders работают между worker'ами;
- HTTP-соединения к EcomKassa переиспользуются, а не создаются на каждый
  запрос;
- пароль пользователя не хранится открытым текстом в Redis/session store;
- настройки имеют устойчивое локальное хранилище SQLite;
- SQLite оптимизирован для редких записей и безопасной работы с двумя
  worker'ами;
- есть rate limit для login и тяжёлых операций;
- есть ограничение исходящей конкуренции к EcomKassa;
- health/logging/metrics позволяют понять, где находится узкое место;
- существующие URL, JSON-контракты фронта, Bearer JWT и бизнес-логика чеков
  не меняются без доказанной необходимости.

Не является целью:
- запускать 3–4 worker без доказанной необходимости;
- переписывать app.js;
- переходить на новый frontend framework;
- менять Atol Online v5 / ФФД / СНО / payments.type;
- менять бизнес-логику чеков, возвратов, ссылок, каталога, отчётов;
- превращать EKLK в самостоятельную систему хранения всех заказов;
- внедрять PostgreSQL без реальной потребности.

================================================================================
2. ЧТО УЖЕ ЕСТЬ И ГДЕ РИСК
================================================================================

По текущему коду ветки exp:

- FastAPI backend;
- app/core/deps.py содержит SESSIONS = dict в RAM;
- session хранит login, password, group_code, firm, selected_store_id;
- JWT проверяется, но после рестарта/на другом worker session может отсутствовать;
- app/clients/ecomkassa.py создаёт собственный httpx.AsyncClient в каждом
  экземпляре EcomKassaClient;
- token EcomKassa сейчас кэшируется только внутри экземпляра клиента;
- settings используют SQLite/локальное хранилище;
- frontend app.js — стабильное монолитное ядро и не должен участвовать в
  масштабировании, кроме точечного критического изменения.

Главные проблемы масштабирования:

1) RAM sessions → multi-worker/restart ломают авторизацию.
2) plaintext password в session → повышенный ущерб при дампе памяти/Redis.
3) AsyncClient на экземпляр → лишние TCP/TLS соединения и риск роста FD.
4) отсутствие централизованного лимита исходящих запросов → можно перегрузить
   EcomKassa быстрее, чем пользовательский UI успеет это заметить.
5) SQLite при активной записи → потенциальные database is locked.
6) отсутствие нормальной наблюдаемости → трудно отличить проблему EKLK от
   проблемы upstream EcomKassa.

5. ЭТАП B — SHARED HTTPX CLIENT
================================================================================

Файлы:
- eklk/app/main.py
- eklk/app/clients/ecomkassa.py
- при необходимости routers, только точечно.

Сделать:

    AsyncClient внутри каждого экземпляра.

B6. На shutdown выполнять await client.aclose().

B7. Не менять публичную семантику методов EcomKassaClient.

Проверка:

- create check;
- payment/invoice;
- orders;
- catalog;
- reports;
- длительный прогон 300–1000 запросов.

Acceptance:

- FD/socket count не растёт линейно с числом запросов.

7. ЭТАП D — УБРАТЬ PLAINTEXT PASSWORD ИЗ SESSION
================================================================================

Это чувствительный этап. Делать после C.

Важно: текущую стратегию обновления токена не менять без необходимости.
В текущем EcomKassaClient уже реализован refresh по HTTP 401 с одним повтором
исходного запроса через get_token(force=True). Не заменять этот механизм
таймерным refresh только ради масштабирования.

Цель session:
    login
    ecom_token (если архитектура после C это допускает)
    group_code
    selected_store_id
    firm

Password не должен храниться в Redis открытым текстом.

Алгоритм:

D1. Сохранить текущую рабочую семантику getToken.

D2. Обычные Ecom-запросы используют действующий token.

D3. Если EcomKassa отвечает 401:
    - выполнить один текущий force refresh/re-auth, если есть безопасный
      способ;
    - повторить исходный запрос один раз;
    - при повторном 401 вернуть контролируемый 401.

D4. Не допускать бесконечного refresh loop.

D5. Не писать token/password в logs.

D6. Проверить race condition при одновременном refresh одного пользователя:
    нужен lock/atomic strategy, чтобы параллельные запросы не создавали
    token-refresh storm.

Не изобретать собственный криптографический протокол.

Acceptance:
- Redis dump не содержит password в открытом виде;
- текущая логика token refresh по 401 продолжает работать;
- 401 корректно обрабатывается;
- параллельный refresh не создаёт storm запросов.

8. ЭТАП E — ОПТИМИЗАЦИЯ SQLITE
================================================================================

PostgreSQL НЕ внедрять и не добавлять без отдельного обоснования.

Причина: локальная БД хранит небольшой объём данных, обращения к ней редкие,
а основная рабочая нагрузка EKLK проходит через EcomKassa API.

Цель: сохранить SQLite как простое и надёжное хранилище settings, устранив
типичные проблемы concurrent writes между двумя worker.

Сделать только после проверки текущего слоя БД:

E1. Определить фактический драйвер/ORM и точки чтения/записи.

E2. Включить WAL mode, если это совместимо с текущим драйвером и deployment.

E3. Настроить разумный busy_timeout, чтобы кратковременная блокировка не
    приводила сразу к database is locked.

E4. Держать транзакции короткими; не выполнять сетевые запросы к EcomKassa
    внутри SQLite-транзакции.

E5. Не держать глобальное соединение SQLite между worker/process.
    Каждый worker должен использовать корректное собственное соединение.

E6. Проверить индексы только по реально используемым полям.
    Не создавать индексы «на всякий случай».

E7. При необходимости сделать GET settings кэшируемым в памяти worker с
    осторожностью. Так как worker два, кэш допускается только для чтения и
    не должен приводить к устаревшим данным после PUT; применять после
    profiling, а не по умолчанию.

E8. Проверить backup/restore SQLite-файла и права доступа к нему.

E9. Сохранить существующий API настроек и degraded-поведение.

Проверка:
- theme light/dark/glass;
- настройки организации;
- выбранный магазин;
- параллельные PUT;
- два worker;
- restart worker;
- backup → restore.

Acceptance:
- нет постоянных database is locked при штатной параллельной работе;
- настройки сохраняются после restart;
- API settings не изменился;
- SQLite-файл не используется как общий объект памяти между worker.

================================================================================
9. ЭТАП F — RATE LIMIT + UPSTREAM PROTECTION
================================================================================

F1. Login:
    жёсткий rate limit по IP.

F2. Create check/payment:
    мягкий rate limit по authenticated user/session.

F3. Исходящие запросы к EcomKassa:
    asyncio.Semaphore на process.
    Начальное значение подобрать тестом, например 50–100, не считать это
    магической константой.

F4. Каждый из двух worker имеет отдельный semaphore. Общий глобальный лимит
    возможен только при отдельной распределённой реализации; на первом этапе
    её не внедрять.

F5. Таймауты едины и конечны.

F6. Не ставить настолько агрессивные лимиты, чтобы обычная навигация,
    F5 и работа нескольких вкладок блокировались.

Acceptance:
- burst login получает 429;
- upstream не получает неконтролируемый burst;
- обычная работа пользователя не деградирует.
